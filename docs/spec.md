# 环回测速（终端→网关）· 需求规格

> 本文件是**需求的唯一来源**。实现方案见交付说明，验收标准见 `docs/verify.md`。
>
> 前一特性（网口对照表）的 spec/verify 见 git 历史 `625015f`。

## 目标

装维上门时，除了「测速」（speedtest，流量走公网，测的是**使用速度**），还要能测出**终端到网关这一段的真实吞吐** —— 不受互联网拥塞、对端服务器负载、ISP 限速策略影响。运营商保障的是**接入速度**，使用速度低不等于接入段有问题，两者必须分开看。

工具新增「环回测速」模块：跑完后完整版报告里出现一级章节**「环回测速」**，把**接入侧速率（终端→网关）**与**使用侧速率（走公网）**并排对照，一眼分清「是接入段慢，还是互联网侧慢」。

一键跑法：交互菜单选「环回测速」，或 `NetPulse.exe --modules loopback`。报告章节标题固定为「环回测速」。

## 范围

### 1. 测量机制（二层注入 + 网关原路回送）

构造 UDP 报文：**目的 IP = 本机 IP**，Ethernet 目的 MAC = 默认网关 MAC，从网卡发出；网关按普通 IP 路由查得「目的地址就是这台客户端」→ 原路送回；本机内核按本地地址认领该报文。

**这不是网关的特殊功能**，而是任何路由器都具备的普通 IP 路由行为（目的地址在网关的直连网段上，回程路由查回来就是「回到我」）。因此**不要求网关装任何东西、不要求网关开 UPnP、不要求管理员权限**。

两条已实测排除的死路：

- 普通 socket 连自己的 IP → 报文 0 包上线（Windows strong host model 就地消费），发不出去 → **发送必须走二层**。
- 网关把「发给网关自己 IP」的报文弹回来 → 实测回 RST，不弹 → **目的地址必须填自己的 IP**。

### 2. 速率口径

- **环回速率 = 线上回送帧数 × 载荷长（1400 字节/帧）× 8 ÷ 采样时长**。计数必须取**线上实际回送的帧**，不能取本机 socket 收包数 —— 二层注入的帧会被本机协议栈额外收一份，直接按 socket 计数会翻倍虚高（已实测：发 500 个，socket 收 1000）。
  - 用**载荷长**而不是整帧长（1442 字节，含以太头 14 + IP 头 20 + UDP 头 8）：speedtest 测的也是 TCP 载荷，两侧都用载荷长，口径才一致，对照结论不被约 3% 的系统性偏差污染。
- **只数「线上真正回送」的帧**：抓包过滤条件限定以太网**源 MAC = 网关 MAC**，本机注入的副本源 MAC 是自己，天然被排除。
- 环回路径 = 终端→网关（出）+ 网关→终端（回），**速率受较慢一侧限制**。**报告与文案必须写明它不是单向带宽**，不得直接当作下载/上传速率解读。
- 采样时长默认 5 秒，`--loopback-duration` 可调（3–30 秒）。

### 2.1 两个必须分清的口径（实测得出，缺一条就会误判现场）

| 现象 | 判据 | 含义 |
|---|---|---|
| 送出去的大半没回来 | **回程完整度 < 70%** | 路径被打满 → 测得值 ≈ **路径真实能力**，可以拿来判链路 |
| 几乎全回来了 | 回程完整度 ≥ 70% | 路径没被压满 → 测得值只是**下限**，不得据此说链路有瓶颈 |
| 施加负载 < 400 Mbps | 实测施加能力 | **工具**没把链路压满（如无线网卡二层注入很慢，实测只能施加约 28 Mbps）→ 低速率是工具能力所限，**不报「终端到网关有瓶颈」** |
| 接入方式是无线 | 网卡描述含 Wireless/WiFi/802.11 | 二层注入在无线上不稳 → 数字标注「仅供参考」，**不判链路瓶颈** |
| 实测值 ≥ 800 Mbps（撞工具上限） | `LOOPBACK_CEILING_MBPS` | 测得值只是**下限**，真实能力可能远高于 800 → 拿它比 2.5G 协商速率必然得出假瓶颈，**同样不报** |

「实测/协商」比值只在**路径被打满 + 有线接入 + 施加负载够 + 未撞上限**时才展示并据此报发现项；其余情况只报数并标注口径。

### 3. 对照基准与结论

- **对照基准**取出口口协商速率（与 linkspeed 模块同源，单位换算走同一个 `_parse_link_speed_mbps`，单一来源）；取不到则该项不显示（不臆造）。- **结论分三类**：
  - 环回速率 ≫ 使用侧速率 → 瓶颈在互联网侧/上游，接入段正常。
  - 环回速率 ≈ 使用侧速率 → 瓶颈在接入段或终端侧。
  - 环回速率 ≪ 出口口协商速率（比值 < 80%，且满足 2.1 的可判条件）→ 终端到网关这一段有瓶颈（网线/水晶头/网口协商掉档/无线信号/网关转发能力），出一条发现项。

### 4. 达标判定（按对端类型自动）

- **scope=access**：确认对端在运营商接入侧。自动判据 = 本机处于 PPPoE/宽带拨号会话且默认路由走该适配器（此时默认网关即 BRAS/BNG）。另提供 `--loopback-scope access` 供自动判不出来时显式声明（专线静态路由场景）。
- **scope=unknown**：其余情况（家用路由器、专线但未声明）。**只报实测值并标明测的是「终端→默认网关这一段」，不判达标。**
- scope=access 且现场模式填了签约带宽时，按 ≥90% 判达标（与现场模式既有口径一致）。
- **绝不**在 scope=unknown 时拿局域网段速率去比签约带宽 —— 百兆网线只有约 115 Mbps，比 1000M 签约带宽差 8 倍，会得出「宽带不达标」的错误结论。

### 5. 报告呈现

- **完整版客户报告新增一级章节「环回测速」**，不是塞进模块卡 —— 有根因时模块卡默认折叠，装维看不到。章节内容：环回速率、对照基准（协商速率）、使用侧速率（speedtest 下行）、一句结论。
- **一页版 brief_v2 第 1 页加一行摘要**，不新增 KPI 格（保 A4 2 页不破）。
- **JSON 导出不新增顶层字段**（模块结果走既有 `tech.raw_results.loopback` 通道），`schema/netpulse-result-v1.2.json` 不变。

### 6. 模块行为与降级

- 模块 key `loopback`，中文名「环回测速」，产出**原生 `DiagnosticResult`**（不走 `_wrap_as_diagnostic_result`）。
- 模块状态只反映「测没测成」：**完成** / **未检测**。**不因速率低而降级模块状态**（速率是数据轴，不是好坏轴）。
- 降级链（全部落到「未检测」，**不扣分**）：
  - 未安装 Npcap → 提示需要 Npcap（与既有抓包功能同款依赖）。
  - 取不到默认网关 / 解析不到网关 MAC / 网关不可达 → 提示具体原因。
  - 网关不回送（采样窗口内线上回送帧数为 0）→ 提示「该网关不回送源目同址报文，无法环回」。
  - 采样被打断 → 提示中断原因；已采到的数据不丢弃，但标注「采样未完成」。
- **加入 `SCORE_EXEMPT_MODULES`**（与 iperf3 同族）：模块状态不参与健康分扣分；模块卡与「主要发现」照常给出发现项。
- **加入 `EXCLUSIVE_NET_MODULE_KEYS`**：并行模式下必须独占网络串行跑（打满链路会压低其它模块测速）。

### 7. 测量能力上限

- 本工具用 Python 走 Npcap 二层发送，**施加负载能力实测约 900 Mbps**（有线 8 线程）；但**无线网卡的二层注入只能施加约 28 Mbps** —— 无线接入下测得的低速率反映的是工具能力，不是链路能力。
- 路径本身也有上限：实测一条千兆办公链路（网关转发能力有限）的环回上限约 95 Mbps，限速扫描证实该值是**路径能力**（回程完整度在低负载时 100%，超 8k pps 后才掉）。
- 实测值达到工具上限（≥800 Mbps）时，报告与结论必须标注「**已达本工具测量上限，实际能力可能更高**」，**不得据此判定不达标**。
- 测得值是**下限**（回程完整度高 / 施加负载不足）时，必须标注「已达本工具测量上限」，不得据此报链路瓶颈。
- **不做**管理员提权档（raw socket + 临时改系统路由表）。它能把速率推满千兆以上，但要求管理员权限、要求改系统路由表，与「装维一键跑」的定位不符。**（已确认）**
- **现场检测模式包含环回测速**（已确认）：现场本就是带宽验收场景；该模块独占串行跑，不影响其它模块的测量结果。

### 8. CLI / 菜单

- 模块选择沿用既有位置参数：`--modules loopback` / `--modules 环回测速` / 菜单序号。
- 新增参数：`--loopback-scope {access,unknown}`（显式声明对端类型，默认 `unknown`）、`--loopback-duration <秒>`（默认 5，范围 3–30）。
- 菜单条目放在「宽带测速」分类**末尾**（tcpcc 之后），避免打乱既有模块序号。

## 不做什么

- 不测「网关以上」的运营商接入段（ONU→OLT→BRAS）—— 客户端侧通常拿不到，除非本机 PPPoE 拨号（那时默认网关即 BRAS）。
- 不做管理员提权档，不改系统路由表。
- 不实现自定义 TCP/IP 栈，不用 raw socket（需管理员）。
- 不依赖网关侧安装 iperf3，不依赖网关开 UPnP。
- 不出「环回 + speedtest」的合并报告文件（两者各自的独立报告照旧）。
- 不改 `loop`「环路检测」模块 —— 它查路由环路，与环回测速是两回事，**术语与 key 不得混淆**。
- 不新增 `LAST_RUN` 依赖。
- 不改健康分口径的既有部分（只把 loopback 加入豁免清单）。

## 硬约束

- **性能**：模块独占跑，采样默认 5 秒；单独跑该模块总耗时 ≤ 20 秒。
- **确定性**：同一台机器同一网络状态，两次采样结果偏差 ≤ 10%（同帧长、同线程数、同采样窗口）；报告里速率保留 1 位小数。
- **不误判**：任何未测成的情况都必须是「未检测」，不得显示为错误/异常，不得扣分。
- **不误导**：速率值必须同时标注「测的是哪一段链路」与「是否已达工具测量上限」；scope=unknown 时报告与文案不得出现「达标/不达标」字样。
- **平台/环境**：Windows 10/11；需要 Npcap（与既有抓包功能同款依赖，缺失即降级）；不要求管理员权限。
- **转义**：模块名、网关 IP/MAC、错误文案进 HTML 时，文本节点用 `_html_esc`，属性值用 `_html_attr`。
- **离线可开**：不引入任何在线资源；样式进 `CSS_CUSTOMER_REPORT` 字面量，不得把整块 CSS 改成 f-string。
- **收口规则**：新 Probe 直接产出原生 `DiagnosticResult`；不新增 `LAST_RUN` 依赖。
- **冻结新增大 Probe 五条对照**：真实用户场景 ✓（电信现场测速）/ 诊断价值 ✓（区分接入段与互联网段）/ 有测试 ✓ / 有报告展示 ✓ / 有降级策略 ✓。

## 术语

- **环回测速**：本文件描述的「终端→网关」吞吐测量。**与既有 `loop`「环路检测」不是一回事**：那个查路由环路，这个测吞吐。
- **终端→网关**：本机 IP 到默认网关这一段（网线/网口协商速率/无线空口/路由器 LAN 口）。
- **接入侧**：运营商承诺带宽所在的网段（ONU→OLT→BRAS/BNG）。客户端侧通常测不到；只有 PPPoE 拨号场景下默认网关才等于接入侧。
- **使用侧**：流量到互联网公网的那一段（speedtest 测的就是这个）。
- **scope**：`access` = 对端确认在运营商接入侧；`unknown` = 默认网关类型未知（家用路由器等）。
- **线上回送帧**：网关按 IP 路由原路送回本机的报文。**速率只按它计数。**
- **协商速率**：网卡与对端协商出的链路速率（`linkspeed` 模块），是「应该能达到」的上限参考，**不是实测值**。
- **工具测量上限**：本工具用 Python 二层发送能达到的速率（实测 1 Gbps 链路上约 820 Mbps）。
