# 网口对照表（端口定位） · 验收要求

> 唯一依据：`docs/spec.md`。本文件只规定「验什么、怎样判定」，不规定「怎么实现」。
> 实现与测试代码不在本文件范围内；执行与结果由交付阶段负责。

## 场景级验收（端到端）

### S1 · 完整版报告出现「网口对照」章节

- 前提：本机有 ≥1 个状态 Up 的物理有线网卡；跑一次全量诊断并导出 HTML
- 动作：打开导出的完整版 HTML
- 期望结果：
  - 「主机信息」与「技术附录」之间出现一个一级章节，标题为「网口对照」，**标题旁标注网口数量**
  - 章节内是一张表，**每个网卡一行**，列为：网口 / 描述 (驱动) / 类型 / 状态 / 协商速率 / 角色 / 提示
  - 「类型」取值只可能是：有线 / WiFi / 虚拟
  - 「角色」取值只可能是：出口口 / 内网口 / WiFi 口 / 虚拟口 / 未插口 / 未判定
    （「未判定」只在取不到默认路由出口时出现，此时有线口不能被标成「内网口」）
- 判定：通过 / 不通过
- 证明方式：场景验证（端到端）+ 机械检查（HTML 文本断言）

### S2 · 出口口唯一且与 Windows 路由一致

- 前提：本机存在默认路由（`0.0.0.0/0`）
- 动作：把报告里角色为「出口口」的那一行的网口别名，与 `Get-NetRoute -DestinationPrefix '0.0.0.0/0' | Sort-Object RouteMetric | Select-Object -First 1` 对应的网卡别名比对
- 期望结果：表中有且仅有一行角色为「出口口」，且其网口别名与上述命令的接口别名逐字相等（大小写不敏感）
- 判定：通过 / 不通过
- 证明方式：机械检查（脚本比对真实命令输出与报告内容）

### S3 · 虚拟网卡不被当成物理口

- 前提：本机装有 VPN/虚拟网卡（构造数据时以虚拟网卡样本覆盖）
- 动作：检查该虚拟网卡所在行
- 期望结果：
  - 角色为「虚拟口」（**前提**：该虚拟网卡不是默认路由出口 —— 承载默认路由时按 S2 优先标「出口口」）
  - 类型为「虚拟」
  - 提示列不出现速率告警文案
  - 它不改变「最差档位」判定（即虚拟口速率再低也不让 linkspeed 模块判为异常）
  - **对照表内该行的档位记 `n/a`**（不适用），既不是「正常」也不是「异常」—— 报正常会让一页版摘要说「各口速率正常」而模块卡同时报档位异常（同一报告自相矛盾），报异常则把虚拟桥接口速率误当物理链路质量问题
  - 该行**不参与**一页版摘要的「异常口数量」统计
- 判定：通过 / 不通过
- 证明方式：场景验证（构造样本数据跑判定函数）

### S3b · 本地桥接网卡（VirtualBox / Hyper-V 等）不是「内网口」

- 前提：构造 `Get-NetAdapter.Virtual = True` 的适配器（如 VirtualBox Host-Only）
- 动作：检查该行
- 期望结果：类型为「虚拟」、角色为「虚拟口」，**不得**出现「内网口」或「有线」——
  客户看到「内网口」会去找一根不存在的网线
- 判定：通过 / 不通过
- 证明方式：机械检查（构造样本跑判定函数）

### S4 · 降速口被标出且措辞不另造

- 前提：构造一个 `speed_mbps = 100` 的有线网卡样本
- 动作：检查该行
- 期望结果：提示列为「协商到百兆, 千兆环境应达 1000 Mbps」（与 `_metrics_linkspeed` 现有文案逐字相同），且该行的档位判定为警告
- **补充要求**：取不到默认路由出口（该口角色为「未判定」）时，该档位提示**仍须逐字保留**；「未能确定默认路由出口, 角色待判定」只在档位提示为空时才补写
- 判定：通过 / 不通过
- 证明方式：机械检查（断言提示文本逐字相等）

### S9 · 软件桥接网卡在报告各处口径一致

- 前提：构造 `Get-NetAdapter.Virtual = True` 的适配器（VirtualBox Host-Only），速率取 10 Mbps（低于有线警告阈值）
- 动作：跑一次 linkspeed 探测并渲染完整版与一页版
- 期望结果：
  - linkspeed 模块卡：类型标签为「虚拟」，提示给出红/黄档的**理由**（档位过低/偏低）+「不代表物理链路」
  - 探测器 issue：文案为「虚拟网卡 …」，**不得**出现「有线适配器」或「检查网线类别」；报告里的「建议」不得是「检查物理连接」
  - issue 的 `type` / `severity` / 数量**不变**（扣分口径不动）
  - 物理有线口的 issue 文案与「建议」逐字不变
- 判定：通过 / 不通过
- 证明方式：机械检查（构造样本跑探测器 + 断言文案）

### S5 · 一页版第 1 页有摘要，且仍是 A4 2 页

- 前提：`tests/_a4_pagecheck.py` 的 5 个场景（`all_timeout` / `many_issues_no_rootcause` / `four_rootcauses` / `healthy` / `rootcauses_with_ports`）均可运行
- 动作：执行 `py -3.13 tests/_a4_pagecheck.py cur`
- 期望结果：
  - 5 个场景各自打印的 PDF 页数**均为 2**
  - brief_v2 的 HTML 第 1 页含网口摘要文本（一行，含出口口网口名与异常口数量）
  - **摘要不得替未连接的物理口宣称速率正常**：未连接的口档位是 `n/a`，没有速率可判。
    物理口一根没插时，摘要不得出现「速率正常」，须出现「无在线物理口」与「N 口未连接」
    —— 交到客户手上的报告不能假绿
  - **摘要与完整版对照表的速率精度必须一致**：同一块网口在两处的速率文本逐字相同
    （如 `115.6 Mbps`，不得一边取整成 `116 Mbps`）
  - **摘要里的口数必须与对照表的列对得上**：「N 口未连接」= 对照表状态列为「未连接」的行数（已禁用不算未连接），「N 个虚拟网卡」= 类型列为「虚拟」的行数 —— 摘要与表不能打架
- 判定：通过 / 不通过
- 证明方式：机械检查（页数脚本 + HTML 文本断言）

### S6 · JSON 顶层有 `port_map`，且与 schema 一致

- 前提：跑一次诊断并导出 JSON
- 动作：执行 `py -3.13 tests/test_schema_export_consistency.py`；再检查导出 JSON 的顶层字段
- 期望结果：
  - 一致性测试 6 个用例全过（exit 0）
  - 导出 JSON 顶层存在 `port_map`，且与 `schema/netpulse-result-v1.2.json` 中声明的结构一致
  - 用标准校验器按该 schema 校验导出 JSON 通过（`additionalProperties: false` 不得报未知字段）
- 判定：通过 / 不通过
- 证明方式：机械检查

### S7 · 恶意网卡名不产生 HTML 注入

- 前提：构造 `name` / `description` 为 `"><img src=x onerror=alert(1)>` 的网卡样本
- 动作：渲染完整版 customer HTML
- 期望结果：输出的 HTML 中不出现 `<img src=x`、不出现 `onerror=alert`；该恶意值以转义后的形式出现在表格文本单元格里
- 判定：通过 / 不通过
- 证明方式：机械检查（新增用例进 `tests/test_html_escape.py`）

### S8 · 单跑 linkspeed 也能拿到出口口

- 前提：只跑 `linkspeed` 一个模块（不跑 `mtu`）
- 动作：查看该次运行的 `linkspeed` 结果与报告
- 期望结果：`egress_interface` 仍有值（不是空串）；报告中「网口对照」章节的出口口行照常判出
- 判定：通过 / 不通过
- 证明方式：场景验证（单独跑一个模块）

## 非目标（回归范围）

以下现有行为**不得被破坏**，改动触及即视为不通过：

- 现有 23 个模块的状态判定、健康分扣分口径、评分等级（A–F）一律不变
- 诊断规则与根因判定（8 条 `_rule_*`）的结论不变
- 完整版报告既有章节的**顺序与内容**不变（只允许新增 1 个「网口对照」章节）
- 一页版客户报告（brief_v2）第 2 页内容不变
- brief v1 报告完全不变
- 既有 `port` 模块（TCP/UDP 端口探测）行为不变
- JSON 既有 19 个顶层字段的取值不变（`port_map` 为新增）
- `tech.raw_results` 结构不变（`linkspeed` 模块内部新增字段除外）
- 控制台编码兜底、调试包导出、异常上报行为不变
- `_tech_appendix_section` 的阈值表**数值不变**（只改其取值来源，不改数字）
- **例外 1（已确认）**：技术附录里「链路速率另在 `_metrics_linkspeed` 硬编码」这句代码位置指引，必须随阈值抽取改为指向新的 `LINKSPEED_*` 常量 —— 留着就是错的指引。除这一句外，附录逐行不变。
- **例外 2（已确认）**：`_short_iface()` 的方括号分支此前**无视 `max_len`**（如 `max_len=24` 时仍返回 29 字符的 `ZeroTier One [9f77fc..225015]`）。已修成遵守 `max_len`，且裁剪时**保留方括号里的区分段**（两台同名不同 GUID 的网卡必须能区分）。
  - 受影响的既有行为：仅「适配器名带方括号」时，`_metrics_mtu` 里 `max_len=18` 的那一行标签会变短（此前溢出 29 字符）。这是兑现函数契约，**不是**本次功能引入的缺陷。
  - 其余 `max_len` 为 32/34/36：名字本身 ≤ `max_len` 的输出逐字不变；**超长**方括号名（如 `Some Really Long Adapter Name [abcdefghijklmnop]`）在这些长度下会从「丢弃方括号段」变为「保留短区分段」，属同一处修复的必然结果。
- **例外 3（本次新增，待确认）**：**软件桥接网卡**（VirtualBox / Hyper-V / WSL 等 `Get-NetAdapter.Virtual = True` 且不属 VPN 产品关键字）在报告里的说法统一改为「虚拟」口径：
  - linkspeed 模块卡的**类型标签**由「有线」改为「虚拟」；提示由档位文案改为「虚拟网卡档位偏低/过低, 不代表物理链路」（保留红黄档的理由，不只是免责声明）。
  - 探测器 **issue 文案**由「有线适配器 … 协商速率仅 N Mbps / 建议检查网线类别」改为「虚拟网卡 … / 虚拟网卡的协商速率不代表物理链路」；报告里的「建议」由「检查物理连接或网卡驱动」改为「确认这个虚拟网卡是否还需要」。
  - 原因：这类网卡根本没有网线，原文案会让装维去查一根不存在的网线；且同一份报告里模块卡说「虚拟」而「主要发现」说「有线适配器」，自相矛盾。
  - **档位判定、issue 的类型/严重度/数量、健康分扣分口径一律不变**（仍按有线阈值算，不改扣分）—— 改扣分口径属另一议题，未在本期处理。
  - 实测影响面：固定 fixture 的 linkspeed 模块卡里**只有这一条指标**的标签与提示发生变化，其余逐字不变。
