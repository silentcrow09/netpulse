# 环回测速（终端→网关）· 验收要求

> 唯一依据：`docs/spec.md`。本文件只规定「验什么、怎样判定」，不规定「怎么实现」。
> 实现与测试代码不在本文件范围内；执行与结果由交付阶段负责。

## 场景级验收（端到端）

### S1 · 完整版报告出现「环回测速」一级章节

- 前提：本机有默认网关且该网关会原路回送源目同址的报文；已安装 Npcap
- 动作：跑一次含 `loopback` 的诊断并导出完整版 HTML
- 期望结果：
  - 「主机信息」与「技术附录」之间出现一级章节，标题为「环回测速」
  - 章节内同时出现：环回速率、对照基准（出口口协商速率）、使用侧速率（speedtest 下行）
  - 章节末尾有一句结论，且结论文字与三者的数值关系一致
  - 速率值旁标注了「测的是哪一段链路」（终端→默认网关）
- 判定：通过 / 不通过
- 证明方式：场景验证（端到端）+ 机械检查（HTML 文本断言）

### S2 · 环回速率不因本地回环副本而翻倍

- 前提：构造一个已知回送帧数的样本（如 N 帧），接收侧同时统计 socket 收包数与线上帧数
- 动作：跑环回测速，检查报告里的环回速率对应的帧计数
- 期望结果：
  - 速率按**线上回送帧数**换算，不是按 socket 收包数
  - socket 收包数恰为线上帧数的 2 倍时（Npcap 注入帧被本机栈额外收一份），报告速率不得是真实值的 2 倍
  - 判定口径可用「发送 500 个 → 线上 1000 帧（含出向）→ socket 收 1000 → 报告速率按 500 个回送帧算」复核
- 判定：通过 / 不通过
- 证明方式：机械检查（构造样本比对换算式）

### S2b · 回程完整度决定测得值是「路径能力」还是「下限」

- 前提：两组样本 —— (a) 回程完整度 0.35（路径被打满）；(b) 回程完整度 0.98（路径没被压满）
- 动作：跑环回测速，检查两组样本的结论与发现项
- 期望结果：
  - (a) 测得值按路径能力呈现，可比照协商速率给出「实测/协商」比值
  - (b) 测得值标注为**下限**（「已达本工具测量上限」），**不得**据此报「终端到网关有瓶颈」
- 判定：通过 / 不通过
- 证明方式：场景验证（构造样本跑判定函数）

### S2c · 无线接入不得被判为链路瓶颈

- 前提：构造 `is_wireless=True` 且实测/协商远低于 80% 的样本
- 动作：跑环回测速并渲染报告
- 期望结果：
  - 报告标注「无线接入, 二层注入能力受限, 数字仅供参考」
  - **不产生**「终端到网关有瓶颈」发现项
  - 不展示「实测/协商」比值（该比值在无线上无判读意义）
- 判定：通过 / 不通过
- 证明方式：场景验证（构造样本跑判定函数）

### S2d · 数字不可判读时，不得下「瓶颈在哪一侧」的结论

- 前提：构造四组样本 —— (a) 无线接入；(b) 路径未打满（`load_limited=True`）；(c) 撞到工具上限（`at_ceiling=True`）；(d) 施加负载不足 400 Mbps（`load_limited=True`），并都配一个公网测速值
- 动作：渲染完整版「环回测速」章节与一页版摘要行
- 期望结果：
  - 完整版结论句**不得**出现「瓶颈在接入段或终端侧」「优先查网线/网口/网关」
  - 结论句改为「不与使用侧对照, 无法判定瓶颈在接入段还是互联网侧」，并说明原因（无线 / 未跑满 / 已达上限）
  - 模块卡指标也不得出现「实测/协商」及「低于 80% 说明终端到网关这一段有瓶颈」的提示（比值本身在不可判读时不展示）
  - **不得**产出「终端到网关这一段有瓶颈」的发现项（否则「主要发现」与章节结论打架）
  - 一页版摘要行**不得**出现「接入侧高于使用侧」的大小对照
  - 理由：注释已写明数字仅供参考，结论却指认瓶颈在哪一侧 —— 同一页自相矛盾，装维会照着结论去换网线
- 判定：通过 / 不通过
- 证明方式：场景验证（构造样本渲染两份报告）+ 机械检查（文案断言）

### S3 · 环回速率受较慢一侧限制，报告不得把它当下行带宽

- 前提：构造一组环回速率低于 speedtest 下行速率的样本
- 动作：检查完整版章节与一页版摘要的文案
- 期望结果：
  - 文案明确说明环回路径含「终端→网关（出）+ 网关→终端（回）」，**速率受较慢一侧限制**
  - 文案**不得**把环回速率称作「下行带宽」或「下载速度」
- 判定：通过 / 不通过
- 证明方式：机械检查（文案断言）

### S4 · scope 判定：只有确认在接入侧才判达标

- 前提：三种样本 —— (a) 本机处于 PPPoE 拨号会话且默认路由走该适配器；(b) 普通家用路由器默认网关；(c) 家用路由器默认网关 + `--loopback-scope access` 显式声明
- 动作：分别跑环回测速并检查报告
- 期望结果：
  - (a) scope=access；(b) scope=unknown；(c) scope=access
  - (b) 的报告与摘要中**不得出现**「达标」「不达标」「签约带宽」任一字样
  - (a)(c) 且现场模式填了签约带宽时：实测 ≥90% 判达标，<90% 判不达标，判定线与现场模式既有口径一致
  - scope=unknown 时即使填了签约带宽，也不判达标
- 判定：通过 / 不通过
- 证明方式：场景验证（构造样本跑判定函数）

### S5 · 未测成一律「未检测」，不扣分、不显示为错误

- 前提：分别构造 (a) 未安装 Npcap；(b) 取不到默认网关；(c) 网关不回送（采样窗口内线上回送帧数为 0）；(d) 采样中途被打断（Ctrl+C 打断，或模块执行超时）
- 动作：跑环回测速，检查模块状态、健康分与报告
- 期望结果：
  - 模块状态一律为「未检测」，**不是**「错误」/「异常」（含超时：超时消息须带 `LOOPBACK_NOT_RUN_MARK`，否则会以「超时/异常」进待办清单）
  - 每个失败原因在模块结果里给出可读的具体原因，且四者互不相同（不得共用一句泛化文案）
  - (a) 的原因必须点名 Npcap（不得报成「适配器不在 Npcap 设备列表里」）
  - (d) 的原因写明「采样未完成」；**已采到的数据不丢弃**（帧数/时长/速率仍进模块结果与 JSON）
  - 健康分不受影响（模块在 `SCORE_EXEMPT_MODULES` 内）
  - 「检测结果一览」徽章里该模块显示为未检测
- 判定：通过 / 不通过
- 证明方式：场景验证（构造样本）+ 机械检查（健康分对比）

### S6 · 速率低不改模块状态，且只在证据充分时出发现项

- 前提：构造四组样本（其余字段相同）——
  - (a) 有线接入、`saturated=True`（回程完整度 <70%，路径确实被打满）、施加负载 ≥ 400 Mbps、协商 1000 Mbps、环回实测 90 Mbps
  - (b) 有线接入、`saturated=False`（回程完整度 98%，路径没压满）、其余同 (a)
  - (c) 无线接入（`is_wireless=True`）、其余同 (a)
  - (d) 有线接入、`saturated=True`、但施加负载仅 120 Mbps（工具没把链路压满）、其余同 (a)
- 动作：分别跑环回测速并渲染报告
- 期望结果：
  - (a) 模块状态仍为「完成」，不降级为警告/异常；出现一条发现项，说明「终端到网关这一段有瓶颈」，并给出实测值与协商速率；健康分不因该发现项扣分（模块在 `SCORE_EXEMPT_MODULES` 内）
  - (b) **不产生**发现项 —— 路径没被打满，测得值只是下限；须标注「已达本工具测量上限」并说明测得值是下限
  - (c) **不产生**发现项 —— 无线接入的环回数字不可用于判定（详见 S2c）
  - (d) **不产生**发现项 —— 施加负载不足时测得值是下限（详见 S2d）；否则「主要发现」与章节结论会自相矛盾
  - 门槛五条件同时成立才出发现项：实测/协商 < 80% **且** 路径被打满 **且** 有线接入 **且** 施加负载 ≥ 400 Mbps **且** 未撞工具上限（≥800 Mbps 时实测值只是下限，拿它比 2.5G 协商速率必然得出假瓶颈）；阈值取自单一来源常量（`LOOPBACK_MIN_RATIO_PCT` / `LOOPBACK_SATURATED_RATIO` / `LOOPBACK_OFFER_MIN_MBPS` / `LOOPBACK_CEILING_MBPS`），不得在呈现层另写一份
- 判定：通过 / 不通过
- 证明方式：机械检查（构造样本跑判定函数）

### S7 · 达到工具测量上限时必须标注

- 前提：构造两组样本 —— (a) 环回速率 ≥ 800 Mbps（`at_ceiling=True`）；(b) 环回速率未达上限但施加负载不足（`load_limited=True`，如施加 120 Mbps、回程完整度 98%）
- 动作：检查完整版章节、一页版摘要与模块卡
- 期望结果：
  - 两组的结论句与章节说明都出现「已达本工具测量上限」字样，并说明实际能力可能更高
  - (b) 额外说明「测得值是下限」
  - 一页版摘要行同样带「已达本工具测量上限」标注（客户只看一页版时不得看到裸数字）
  - 两种情况下**不得**出现「不达标」结论
  - 两种情况下也**不得**下「瓶颈在接入段或终端侧」的两侧对照结论（见 S2d）
- 判定：通过 / 不通过
- 证明方式：机械检查（文案断言）

## 非目标（回归范围）

以下现有行为**不得被破坏**，改动触及即视为不通过：

- 现有 23 个模块的状态判定、健康分扣分口径、评分等级（A–F）不变（`loopback` 作为新增豁免模块加入，不改动既有模块的计分）
- 诊断规则与根因判定（8 条 `_rule_*`）的结论不变
- 完整版报告既有章节的**顺序与内容**不变（只允许新增 1 个「环回测速」章节）
- 一页版客户报告（brief_v2）第 2 页内容不变，第 1 页只允许新增一行环回摘要；brief v1 报告完全不变
- 既有 `loop`「环路检测」模块行为不变
- 既有 `iperf3` 模块行为不变（环回测速不得复用其状态或配置）
- JSON 既有顶层字段的取值不变（无新增顶层字段）
- `tech.raw_results` 结构不变（`loopback` 模块为新增 key）
- 控制台编码兜底、调试包导出、异常上报行为不变
- 既有 `speedtest` 模块的测速结果与呈现不变
